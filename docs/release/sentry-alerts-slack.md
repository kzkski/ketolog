# Sentry アラート最小セットと Slack 通知（P1 / P2）

**目的**: 無料プラン前提で通知ノイズを抑えつつ、重大障害だけを Slack に上げる。実際のルール作成・閾値調整は **Sentry プロジェクト**で行い、本書は **正本の仕様**とする。

**関連**: ヘルス定期実行は [`.github/workflows/production-health-check.yml`](../../.github/workflows/production-health-check.yml)。一次切り分けの手順全体は Issue #169（Runbook）で整備する想定。

---

## 1. 深刻度の定義（P1 / P2）

| 区分 | 意味 | 対応の目安 |
|------|------|------------|
| **P1** | 本番のコアが止まる、またはデータ欠損・セキュリティに直結しうる | 即時確認（可能なら 30 分以内に一次切り分け） |
| **P2** | 一部ユーザー・周辺機能、または性能劣化。単発ノイズの可能性あり | 営業時間内の初動でよい（連続発火時は P1 に昇格を検討） |

---

## 2. Slack 連携とテスト通知

Sentry の UI は更新されるため、用語は [公式: Slack の統合](https://docs.sentry.io/product/integrations/notification-incidents/slack/) を優先して読み替える。

1. Sentry で対象の **Organization / Project** を開く。
2. **Settings**（歯車）→ **Integrations** → **Slack** を開き、ワークスペースを **Install** する。
3. 通知先の **チャンネル**を選ぶ（`#incidents` など。公開／プライベートはチーム方針に従う）。
4. 任意の **Issue Alert** または **統合のテスト送信**機能で **Slack にテスト通知が届く**ことを確認する（メニュー名は「Send notification」「Test」等。見つからない場合は下記 5 のいずれかのルールに **Send a Slack notification** アクションを付け、意図的に小さなテスト Issue を発生させて確認する）。

**完了条件「テスト通知が Slack で受信できる」**は、上記 4 までで満たす。

---

## 3. 通知スパム抑制（全ルール共通の方針）

次を **各ルール**で必ず検討する（Sentry の「アクションの間隔」「1 Issue あたりの通知上限」等。名称はプラン・UI 版で異なる）。

| 方針 | 例 |
|------|-----|
| **時間窓** | 「10 分以内に N 件」など、単発スパイクだけでは鳴らさない |
| **連続性** | 同じ Issue が短時間に連続したときだけエスカレーション |
| **環境** | `production`（および必要なら `staging`）に限定。開発用環境は除外 |
| **サンプリング** | パフォーマンス系は `tracesSampleRate` が 0 より大きい環境でのみ意味がある（本リポジトリのサーバ設定は [`sentry.server.config.ts`](../../sentry.server.config.ts)） |

## 4. 最小 5 本のアラート（仕様）

`/api/health` の失敗時は [`src/app/api/health/route.ts`](../../src/app/api/health/route.ts) で `Sentry.captureException` され、タグ **`route`** = `/api/health`、**`check`** = `supabase` が付く。

以下は **Metric alerts** と **Issue alerts** のどちらでも実現できる場合は、プランに合わせてよい。フィルターは **Issue / Event のプロパティ**として指定する。

### 4.1 新規の未処理エラー（P1）

| 項目 | 内容 |
|------|------|
| **狙い** | これまで無かった種類の本番エラーが出たら即知る |
| **条件の例** | **新規 Issue が作成された**（First seen）かつ **environment** が `production` |
| **追加フィルタ（推奨）** | `isUnhandled` が true（または Sentry 上の同等フィルタ） |
| **抑制** | 同一 Issue への Slack は **30 分に 1 回まで** 等 |

### 4.2 ヘルスチェック連続失敗（P1）

| 項目 | 内容 |
|------|------|
| **狙い** | DB 疎通失敗など、GitHub Actions の 5 分監視と整合する「連続障害」 |
| **条件の例** | タグ **`route` = `/api/health`**（または **`check` = `supabase`**）のイベントが **10 分以内に 2 回以上** |
| **抑制** | 上記時間窓を満たすまで通知しない。復旧後は自動解消に任せる |

### 4.3 認証まわりのエラー急増（P2）

| 項目 | 内容 |
|------|------|
| **狙い** | OAuth コールバックやログイン経路の異常な増加 |
| **条件の例** | **transaction** または **URL** に `auth/callback` または `login` を含むイベントが **15 分で 20 件超**（ベータのトラフィックに合わせて N を調整） |
| **抑制** | 閾値は週次で見直し。単発バーストは P1 に上げない |

### 4.4 API / サーバー応答の遅延悪化（P2）

| 項目 | 内容 |
|------|------|
| **狙い** | パフォーマンスの継続的な悪化 |
| **前提** | Performance / Transactions がプロジェクトに届いていること（サンプリングあり） |
| **条件の例** | `http.server` 系トランザクションの **p95 レイテンシ** が **5 分窓で 3000 ms 超**（閾値は実測で調整） |
| **抑制** | 短いスパイクのみのときは発火しないよう、連続 2 窓以上などの条件を付与 |

### 4.5 同一エラー（同一 Issue）の急増（P1）

| 項目 | 内容 |
|------|------|
| **狙い** | デプロイ不具合・無限リトライ等の「同じ例外の連打」 |
| **条件の例** | **同一 Issue** が **1 時間に 50 イベント超**（N は規模に合わせて調整） |
| **抑制** | 初回は 4.1 で既に飛ぶため、本ルールは **「頻度が異常なときだけ」** に寄せ、Slack 文面で Issue URL を必ず含める |

## 6. 既知の制約

- Sentry / Slack の **無料枠・プラン**によっては Metric alert やアクション数に制限がある。制限時は **Issue アラート**に寄せ、条件を粗くしてから徐々に絞る。
- 認証フローは **リダイレクトのみで例外を投げない**経路がある。その場合は 4.3 は **クライアント・サーバー両方のエラー**を対象にし、Discover でクエリを調整する。
