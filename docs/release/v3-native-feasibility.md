# v3 ネイティブアプリ化検討メモ（非ブロッキング）

Issue: [#272](https://github.com/kzkski/ketolog/issues/272)  
親Issue: [#263](https://github.com/kzkski/ketolog/issues/263)

このドキュメントは、v3 一般公開に向けて **ネイティブアプリ化を判断するための材料整理**を目的とする。  
本版では #272 の受け入れ条件に合わせ、KPI 定義・測定手順・Go/No-Go 提案を追加する。

## 位置づけ

- v2 のベータ公開ゲートをブロックしない（非ブロッキング）。
- v3 での Go/No-Go 判断を迷わないため、論点と前提を先に揃える。
- 実装着手時は Issue を作成し、本書は判断の正本として更新する。

## 目的

- PWA 継続 / ネイティブ化 / ハイブリッドの選択肢を比較可能にする。
- 一般公開時点のユーザー体験と運用体制に対し、どの方式が妥当かを判断できる状態にする。

## 検討観点

### 1. プロダクト観点

- ネイティブ化で改善したい体験は何か（例: 通知、カメラ利用、継続率）。
- 現行 PWA で代替可能な範囲と、代替しにくい範囲の切り分け。
- v3 ローンチで必須にする機能と、後続リリースでよい機能の分離。

### 2. 技術観点

- Next.js / Supabase / 認証基盤の再利用方針。
- 候補方式（React Native / Expo / Flutter / 完全ネイティブ）の比較軸。
- セッション管理、オフライン同期、更新配布、監視基盤の設計方針。

### 3. 運用観点

- App Store / Google Play 審査対応の要件確認。
- リリース運用（署名、証明書、ロールバック、クラッシュ解析）の整備項目。
- サポート導線・問い合わせ・障害時の一次対応フロー。

### 4. 法務・コンプライアンス観点

- モバイル配布時の利用規約・プライバシーポリシー更新範囲。
- ストア要件（アカウント削除導線など）の反映有無。
- 外部 API 利用条件（OFF 等）の継続遵守方針。

### 5. コスト・体制観点

- 開発/保守工数、QA端末、CI/CD の追加コスト。
- 継続運用に必要な担当体制（開発・運用・サポート）。
- 収益化前提が未確定な段階で許容する固定費の上限。

## 実証 KPI 定義（#272）

ネイティブ化継続判断は、以下 4 指標を最小セットとする。  
測定対象の標準シナリオは「ログイン -> Today 記録 CRUD -> 再起動後表示」とする。

| KPI | 定義 | 計測方法 | 継続判断の目安 |
| --- | --- | --- | --- |
| 体感速度 | 主要操作（起動、一覧表示、保存、再表示）の待ち時間に対する体感評価 | iOS 実機で同一シナリオを 3 回以上実施し、操作ごとに「速い / 普通 / 遅い」を記録。必要に応じて画面録画で補助。 | 「遅い」評価が連発しない（主要操作の大半が「速い or 普通」） |
| 操作完了率 | 標準シナリオを途中離脱・手戻りなく完了できる割合 | 1 セッションを 1 試行として、成功 / 失敗を記録。失敗理由を分類（認証・同期・UI導線など）。 | 失敗要因が局所的で、改善可能な粒度に収まる |
| クラッシュ | 操作中にアプリが異常終了する頻度 | TestFlight 実機試験と配布ログ（Issue コメント）で異常終了件数を記録。 | 重大クラッシュ 0 を目標（PoC 期間中） |
| 開発効率 | PoC スコープの実装を、許容工数で回せるか | 子Issue #264-#271 の完了速度、手戻り回数、運用ドキュメント整備状況を確認。 | 追加投資で v3 スコープに展開可能と判断できる |

## 計測手順（固定）

1. TestFlight 配布済みビルドを iOS 実機で起動する。
2. 同一シナリオ（ログイン -> Today CRUD -> 再起動）を 3 試行以上行う。
3. 試行ごとに以下を記録する。
   - 体感速度（速い / 普通 / 遅い）
   - 成功 / 失敗（失敗時は理由）
   - クラッシュ有無
4. 実装・運用面は #264-#271 の Issue/PR と `docs/release/ios-testflight-distribution.md` を根拠に確認する。
5. 最後に「継続 / 見送り / 条件付き継続」を 1 つ選び、条件がある場合は解除条件を明示する。

## 暫定評価（2026-04 時点）

### KPI 観測（暫定）

- 体感速度: **概ね良好（定性的）**  
  ログインから Today 操作までの体験は PoC 目的を満たす水準。厳密なミリ秒計測は次フェーズで補強する。
- 操作完了率: **主要シナリオは完了可能**  
  親Issue #263 の DoD（ログイン -> Today CRUD -> 再起動表示）を満たす実装が完了。
- クラッシュ: **重大クラッシュ未報告（PoC 期間）**  
  現時点は配布導線・手順整備までを優先し、クラッシュ解析の定量化は次フェーズ課題。
- 開発効率: **PoC として成立**  
  #264-#271 を短期間で完了し、共有基盤・同期最小挙動・TestFlight 配布運用まで到達。

### Go / No-Go 提案

- 判定: **条件付き継続（Go with conditions）**
- 理由:
  - 中核体験（認証 + Today 記録 + 基本同期 + 配布導線）は成立した。
  - 一方で、定量モニタリング（クラッシュ率・操作時間の計測基盤）は未整備で、即フル移行判断には情報が不足する。
- 継続条件（次フェーズの入口条件）:
  1. iOS 実機での KPI 記録テンプレートを運用し、最低 1 スプリント分の記録を蓄積する。
  2. クラッシュ/エラーの定量監視（例: Sentry の mobile 監視）を導入し、週次で確認できる状態にする。
  3. Web/PWA と mobile の役割分担（どこまでを mobile で提供するか）を v3 スコープとして固定する。

## 判断アウトプット（最小）

- 方針: `条件付き継続`
- 採用理由: 中核 UX は成立したが、定量モニタリング整備を先に行うことで、v3 の投資判断を誤りにくくするため。
- v3 スコープ: mobile はクイック記録導線を優先し、Web は高密度編集・管理導線を継続担当とする。
- 実装開始条件（Go 条件）: 上記「継続条件」3 項目が満たされること。
